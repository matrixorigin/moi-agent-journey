# 页面性能改进

已在副本 `page.html` 修复循环中反复重写整个列表的问题；输入文件未修改。保留标题、10,000 条订单文案及 0–9999 的顺序。

原代码每次执行 `innerHTML +=` 都会序列化已有内容，再解析并替换列表；改为 `rows.map(...).join("")` 后一次赋值。列表的 HTML 处理量由随条数近似平方增长，改为线性增长，同时减少 DOM 查询与写入次数。

使用本机 Chrome headless，交替运行原版与修改版各 3 次，以 `performance.now()` 测量内联列表构建脚本耗时：

| 轮次 | 原版（毫秒） | 修改版（毫秒） |
|---|---:|---:|
| 1 | 9955.00 | 2.20 |
| 2 | 10287.90 | 2.30 |
| 3 | 10133.20 | 2.30 |

中位数为原版 10133.20 毫秒、修改版 2.30 毫秒。原始数据见 `measurements.json`，复现脚本为 `benchmark.py`。

六次运行均验证了列表数量为 10,000，并逐项核对 `订单 i` 的文本和顺序，首尾分别为“订单 0”和“订单 9999”。

测量限制：本次是单台机器、同一浏览器、三轮本地微基准，统计范围包括脚本执行及极少量相邻解析开销，排除 Chrome 启动、绘制、网络、完整加载时间及真实用户交互；不能据此推断 LCP、INP 或端到端加载加速倍数。10,000 个 DOM 节点仍会产生后续布局和绘制成本，本次未改分页或虚拟化。
