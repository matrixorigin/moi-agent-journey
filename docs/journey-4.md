# Journey-4：100 个业务智能体任务

这组用例测试用户的真实工作目标，不是桌面软件按钮或功能点。`J4-01…J4-100` 一一映射原始 `T001…T100`，分为产品需求、调研决策、数据分析、项目流程、营销内容、销售客户、文档多模态、财务采购、代码自动化、本地文件与综合任务十类。

材料由本次用户授权的 Desktop-100 评测生成，业务组织、人物、金额、交易、日志和代码仓库均为合成样例。公开调研读取的网页是任务目标，不代表这些产品的固定事实或取得其内容再分发的授权。没有引入真实客户资料、QA 凭据或其他评测项目的受限数据。原始 198 个样例逐字节保留在 `_materials/samples/`，`manifest.json` 记录原文件大小和 SHA256；没有复制每个会话的全套重复输入。

每项 `case.json` 声明所需资产及 SHA256、原始业务要求、交付物和独立验收规则。准备阶段从版本化的本地材料复制到 `work/inputs/`，无需易变下载地址；081–090 与096带完整合成源码仓库，070带64个 shared 资料，091–094带对应目录。受测会话只收到本项输入包与任务，**不会收到 rubrics、历史结果、评分或参考答案**。ASR 用例不提供 meeting.txt。

输入 ZIP 先上传到私有 Catalog，随后必须作为**聊天消息附件**发送：消息包含 `kind=file` 和 `moi://files/<file_id>`，且与 `metadata.files` 绑定同一上传记录。只在提示词写文件 ID 或粘贴输入全文不满足附件输入协议。`Execution.send` 在 Business-100 各会话首轮提交前校验附件绑定，缺失或不匹配则报框架错误并阻止模型请求；已知旧脚本的全文内联标记也会被拒绝。`journey.chat_attachments` 提供可复用的附件构造和校验，供 Desktop 计时适配使用。离线回归覆盖100项任务消息、错误绑定及执行器实际提交载荷；这些检查不等于已验证智能体实际读取了文件。

本地旧 Desktop 计时曾使用 Catalog 引用/正文内联，与本附件协议不同；其耗时必须单独标记，不作为正式 Journey-4 附件输入整轮耗时。文件清理是另一项边界：现有流程会取证并归档会话，上传输入和发布产物按仓库原有策略保留诊断，沙箱中间文件删除尚未执行或验证，不能将 `cleanup=archived` 解读为文件已清理。

原任务文字保留，QA 适配将 `samples/` 映射到 `inputs/samples/`、`results/Txxx` 映射到 `outputs/`，要求 `result.md`、`execution.md` 及实际文件打包为可下载 `journey-output.zip`。091/093先复制到本次可写暂存目录，再在其内实际移动/重命名；明确覆盖附件的一般只读条款，原 inputs 保持不变。这些隔离、输入可达性和交付协议变化意味着新 QA 不是历史 Desktop 的逐字相同重跑。

## 执行与验收

套件使用现有 office 执行器和事件/附件取证，最大并发3，每项 QA 总预算1800秒，包含主任务、证据提取和语义评审。每项一个新的主任务会话，一次提交，不自动修正重跑。另建全新评审会话检查实际交付、原始材料与逐项规则；评审不读 Codex 基线，也不修改原成果。主任务时间和评审时间分别记录，工具统计按 judge 阶段分开。

文档、表格、PDF、图像和文本由无网络、无 QA 凭据、只读挂载的 judge 容器提取，评审“通过”必须附实际提取成果中的原文证据，伪造引用或缺失规则视为验收器错误。原二进制也提供给评审用于看图等核验。结构验收另行检查文件可解析/Office可渲染、两页PDF、十页PPT及逐页备注、可编辑正文、Excel公式、CSV结构/总额、真实代码交付、移动与改名的文件集合/hash、实际缩图尺寸等。不会在宿主机执行受测者提交的脚本。

**语义评审尚未校准，不能作为发布门禁或统一能力分。** 原文引用存在不能证明判断正确，执行记录由作答者写出也不能独立证明执行。重要案例应结合原始工具事件、实际产物及人工复核。模型判词无效或提取失败记框架/验收错误；正常完成验收但业务不满足记失败。未知/缺失不当通过，环境失败与业务错误保留原始证据。

离线检查（不访问 QA）：

```sh
python3 -m unittest discover -s tests -v
python3 -m journey.catalog plan journey-4
python3 -m journey.catalog prepare J4-01
docker build -t moi-journey-judge -f judge/Dockerfile .
# tests_judge 的容器参数参见 ci.yml
```

真实 QA 需 `MOI_BASE_URL`、`MOI_PAT` 与已加载的 judge 镜像：

```sh
python3 -m journey.run_case J4-01
python3 -m journey.validate J4-01
python3 -m journey.report case J4-01
python3 -m journey.publish
```

在 `Agent journeys QA` 选 `journey-4` 可运行全组。合入后也会进入既有每六小时的 all 定时回归；100个主任务加100个评审会话会增加调用与队列时长，最坏主任务预算约16.7小时（100×30分钟÷3），另加准备/验收/清理。PR 不触发真实 QA。本次接入不填造新的 QA 成绩。

## 报告里的 Codex 对照

`baselines/journey-4/codex-2026-10-29.json` 保存历史固定模型 `gpt-6.1-sol` 的100项人工成果验收：99通过、1部分通过（T091只复制未移动）。同时保留历史 MOI 人工验收49通过/50部分通过/1阻塞，方便追踪已知差异。它们属于2026-10-29的历史成果，不计入本次 QA 的分母或通过数。

基线附逐项评语、开始/完成观察时间、原始交付物哈希清单及200份公开版 `result.md`/`execution.md`，本地个人路径已替换，并同时保留原文与公开版本哈希。该提交只携带正文和执行记录，不声称附有全部二进制交付或完整底层工具流；其他产物以原哈希清单留痕。

每次汇总生成 `comparison.html/.md/.json/.csv`，并在 `summary.md/.json/.csv` 加入 Codex 对照。HTML可点开每项 Codex 正文和执行记录，下载包含基线副本。未产生本次结果时显示“结果缺失/未运行”，仍计入本次缺失结果。历史人工“部分通过”和本次自动检查失败不是同一量表，不输出直接胜率。

Codex是本地macOS独立会话，历史MOI有重试/复用、云端输入工具也不同。观察到的Codex起止时间包含轮询延迟与并发，不等于QA的 `task_seconds`；报告保留原始观察时间，明确 `timing_comparable=false`、`speed_ratio=null`，不制造速度倍数或纯模型排名。

仅预览历史对照时可调用 `journey.comparison.build` 并传入未运行行；不要用正常聚合命令的缺失报告冒充真实执行报告。本文档、基线与 case 修改均受版本控制，主任务规格哈希包含rubric、输入hash、模型与预算。
